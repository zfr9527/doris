## 实验设计

**核心问题**：同样合法的 prune，"明显安全" vs "勉强安全" 的 key 性能收益差多少？

固定 SQL（`group by good_key, k2, k3, k4, k5, k6`），只改变 `good_key` 的统计信息：

| Case | good_key 配置 | hot_value | NDV | 裕量等级 | 含义 |
|------|--------------|-----------|-----|---------|------|
| VM01 | hot=0, NDV=60000 | 无 | 60000 | **高裕量** | 远超 isBalanced 阈值 |
| VM02 | hot=0.02, NDV=20000 | `1 :0.02` | 20000 | **中裕量** | 有轻微倾斜 |
| VM03 | hot=0.049, NDV≈阈值+100 | `1 :0.049` | 阈值边界 | **低裕量** | 勉强通过 isBalanced |

> k2~k6 均注入 `hot_values='1 :0.10'`（skew），确保 optimizer 一定选中 `good_key`。

### 阈值计算
- 3 BE × 8 pipeline = 24 instances
- ndvThreshold = 24 × 512 = **12,288**
- VM03 NDV = 12,288 + 100 = **12,388**（刚好超过阈值）

## 关键结论

### 1. 高裕量下有轻微正向收益（1.04x）
VM01（NDV=60000，无 hot value）是最"安全"的裁剪场景，获得 **3.4%** 的加速（105ms），在全 bigint 表上属于正常水平。

### 2. 中低裕量下收益消失（0.98x）
VM02/VM03 的 Speedup 均为 0.98x，属于测量噪声范围内的微小劣化：
- **VM02**（NDV=20000，hot=0.02）：轻微倾斜导致分布质量下降
- **VM03**（NDV=阈值+100，hot=0.049）：数据分布极不均匀，裁到此列反而增加了 hash 碰撞

### 3. 安全裕量对实际性能的影响有限

| 观察 | 分析 |
|------|------|
| VM01 vs VM02/VM03 差距 ≈ 6% | 裕量差异只影响 Shuffle 的数据均衡性 |
| 绝对值差异 < 200ms | 在 3 秒级查询中占比很小 |
| 全 bigint 场景的限制 | hash 本身成本低，分布不均的代价也小 |

### 4. 勉强通过 isBalanced 不会导致严重劣化
VM03（NDV 刚过阈值，hot=0.049）只有 0.98x，即 -56ms 的微量劣化，**没有出现严重性能回退**，说明 isBalanced 阈值设计是合理的。

## 建议

1. **isBalanced 阈值无需调整**：边界 Case（VM03）未劣化，说明现有设计安全
2. **生产环境中裕量影响会放大**：如果包含 varchar/string 列，分布不均带来的 hash 碰撞代价更大，裕量差异会更明显
3. **可作为保底安全测试**：本实验证明即使 key 裕量极低，也不会出现严重劣化
